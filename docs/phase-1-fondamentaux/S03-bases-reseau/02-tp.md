## Partie A – Lire sa configuration (≈ 20 min)

**But :** savoir à quoi ressemble la configuration d'un poste qui fonctionne.

1. Ouvre une invite de commandes (`cmd`) et tape `ipconfig`, puis `ipconfig /all`.
2. Remplis le tableau.

| Information | Valeur | Où la lire |
|---|---|---|
| Adresse IPv4 | | `ipconfig` |
| Masque | | `ipconfig` |
| Passerelle par défaut | | `ipconfig` |
| Adresse MAC (adresse physique) | | `ipconfig /all` |
| Serveur DNS | | `ipconfig /all` |
| Serveur DHCP et durée du bail | | `ipconfig /all` |

**J'anticipe.** Si la ligne « Adresse IPv4 » affichait `169.254.x.x`, que cela signifierait-il ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Le poste n'a **pas obtenu d'adresse d'un serveur DHCP** et s'est attribué lui-même une adresse **APIPA** (`169.254.0.0/16`). C'est le signe d'un problème de connexion ou de DHCP, pas d'un poste correctement configuré.

</details>

**Je comprends.** Pourquoi la passerelle par défaut est-elle dans le **même réseau** que l'adresse IP du poste ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Le poste doit pouvoir **joindre directement** la passerelle (sans passer par un routeur) pour lui confier tout ce qui sort de son réseau. Une passerelle située dans un autre réseau est injoignable : le poste ne peut plus sortir.

</details>

## Partie B – Localiser une panne avec `ping` (≈ 30 min)

**But :** tester **de proche en proche** pour savoir où ça casse.

`ping` envoie des messages ICMP « echo request » et attend des « echo reply ». Il mesure la **latence** (en ms) et le **taux de perte**.

| Étape | Commande | Ce qu'on vérifie | Si ça échoue |
|---|---|---|---|
| 1 | `ping 127.0.0.1` | La pile réseau du poste | Problème de pilote ou de système sur le poste |
| 2 | `ping` *ta passerelle* | La liaison locale (câble, switch) | Câble débranché, switch, mauvaise adresse |
| 3 | `ping 8.8.8.8` | La sortie vers Internet (sans DNS) | Problème de la box ou du fournisseur d'accès |
| 4 | `ping www.google.fr` | La résolution de noms (DNS) | Si l'étape 3 réussit : problème de **DNS** |

**J'anticipe.** Les étapes 1 à 3 réussissent, l'étape 4 échoue. Quelle couche, quel service ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Le réseau fonctionne jusqu'à Internet, mais le **nom** n'est pas traduit en adresse : le service **DNS** est en cause (serveur DNS injoignable ou mal renseigné). Ce raisonnement « de proche en proche » évite de chercher au hasard.

</details>

**Manipulation.** Exécute les quatre étapes et remplis :

| Étape | Résultat (réussi / échoué) | Latence moyenne | Pertes |
|---|---|---|---|
| 1 | | | |
| 2 | | | |
| 3 | | | |
| 4 | | | |

**Je comprends.** Quelles informations donnent « temps » et « TTL » dans la réponse d'un `ping` ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Le **temps** est la durée aller-retour (la latence) en millisecondes. Le **TTL** (*time to live*) est un compteur décrémenté par chaque routeur traversé : il évite qu'un paquet tourne indéfiniment ; sa valeur restante donne une idée du nombre de routeurs traversés.

</details>

## Partie C – `tracert`, `nslookup`, `netstat` (≈ 30 min)

**But :** trois autres outils, trois questions différentes.

| Outil | Question à laquelle il répond | Commande à tester |
|---|---|---|
| `tracert` (Windows) / `traceroute` (Linux) | Par quels **routeurs** passent mes paquets ? où ça ralentit ? | `tracert www.google.fr` |
| `nslookup` | Quelle **adresse IP** correspond à ce nom ? quel serveur DNS répond ? | `nslookup www.microsoft.com` |
| `netstat -an` | Quelles **connexions** et quels **ports en écoute** ont mon poste ? | `netstat -an` |

**J'anticipe.** Dans une ligne `tracert`, que signifie `* * *` ? Est-ce forcément une panne ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Le routeur concerné **n'a pas répondu** aux paquets de test. Ce n'est **pas forcément une panne** : beaucoup de routeurs sont configurés pour ne pas répondre à ces messages. Si les sauts suivants répondent, le chemin fonctionne.

</details>

**Manipulation.** Réponds :

1. Combien de sauts jusqu'à `www.google.fr` ? ______ Quel est le premier (ta passerelle ?) ? ______
2. Adresse IP de `www.microsoft.com` ? ______ Serveur DNS qui a répondu ? ______
3. Combien de connexions à l'état `ESTABLISHED` ? ______ Quel port **local** et quel port **distant** pour une connexion web (443) ? ______ / ______

**Je comprends.** Que signifie `LISTENING` dans `netstat` ? Pourquoi est-ce important pour la sécurité d'un serveur ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

`LISTENING` : un programme **attend des connexions** sur ce port (un service). Chaque port en écoute est une **porte d'entrée possible** : sur un serveur, on ne laisse ouverts que les services nécessaires.

</details>

## Partie D – Regarder passer les trames avec Wireshark (≈ 40 min)

**But :** voir ce qu'un `ping` ou une résolution de nom envoient réellement sur le câble.

**Wireshark** est un **analyseur de trames** : il capture et décode ce qui passe sur une carte réseau. Il fait partie des outils attendus d'une infrastructure SISR (annexe II.E du référentiel).

1. Lance Wireshark, choisis la **carte réseau** connectée au réseau de la salle (celle dont le compteur bouge), clique sur **Démarrer la capture**.
2. Dans la barre de filtre d'affichage, tape `icmp` puis Entrée.
3. Dans l'invite de commandes, lance `ping` vers ta passerelle (4 paquets).
4. Arrête la capture. Repère une **requête** (`Echo (ping) request`) et sa **réponse** (`Echo (ping) reply`).

**J'anticipe.** Quelles adresses MAC et IP vas-tu voir dans la requête ? Et dans la réponse ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Requête : source = ton poste (IP et MAC), destination = la passerelle (IP et MAC). Réponse : les rôles s'**inversent**. La passerelle est dans ton réseau, donc la MAC de destination est bien **celle de la passerelle** et pas celle du serveur final : à ce niveau, la couche 2 ne parle qu'au prochain équipement.

</details>

5. Sélectionne la requête et déplie dans le volet central les couches : **Frame**, **Ethernet II**, **Internet Protocol**, **Internet Control Message Protocol**. Remplis :

| Couche | Champ | Valeur relevée |
|---|---|---|
| Ethernet II (couche 2) | Adresse MAC source | |
| Ethernet II (couche 2) | Adresse MAC destination | |
| IP (couche 3) | Adresse IP source | |
| IP (couche 3) | Adresse IP destination | |
| IP (couche 3) | TTL | |
| ICMP | Type | |

6. Efface le filtre, tape `arp`, vide ton cache (`arp -d *` en invite administrateur) puis refais un `ping` vers la passerelle. Repère la **requête ARP** (« Who has … ? Tell … ») envoyée en **diffusion** et la réponse (« … is at … »).
7. Filtre `dns`, lance `nslookup www.microsoft.com` : repère la **requête** et la **réponse** DNS (port UDP 53).

**Je comprends.**

| Question | Réponse |
|---|---|
| Pourquoi la requête ARP est-elle envoyée en diffusion (`ff:ff:ff:ff:ff:ff`) ? | ______________________ |
| Quelle couche du modèle OSI correspond à chaque bloc que Wireshark déplie (Ethernet, IP, ICMP, UDP, DNS) ? | ______________________ |
| Pourquoi voit-on la requête DNS **avant** le premier paquet vers le site web ? | ______________________ |

<details markdown="1">
<summary>Éléments de réponse</summary>

- Le poste connaît l'adresse IP de la passerelle mais **pas son adresse MAC** : il interroge **tout le réseau local**, et seule la machine concernée répond.
- Ethernet : couche 2 ; IP et ICMP : couche 3 (ICMP voyage dans un paquet IP) ; UDP : couche 4 ; DNS : couche 7.
- Il faut d'abord **traduire le nom en adresse IP** avant de pouvoir envoyer un paquet à ce serveur.

</details>

> [!WARNING]
> Une capture peut contenir des données personnelles (sites visités, noms d'utilisateurs). Ne la partage pas hors du cadre du TP et ne capture que le temps nécessaire.

**Point de contrôle :** une capture d'écran datée montrant la requête et la réponse ICMP avec les couches dépliées, et une autre montrant l'échange ARP.
