## Partie A – Préparer le réseau (≈ 30 min)

**But :** quatre machines qui se voient chacune dans leur réseau, et un pare-feu qui route.

0. **Préparation (une fois, avec Internet).** Les réseaux internes de VirtualBox n'ont pas d'accès à Internet : installe d'abord les paquets, avec la carte de chaque VM en **NAT** : `sudo apt update && sudo apt install -y tcpdump curl` sur toutes les machines, `apache2` sur **SRV-DMZ** et sur **EXT**, `nftables` sur **FW**. (Ou utilise les VM préparées par l'enseignant.)
1. Dans VirtualBox, règle ensuite les cartes réseau de chaque VM en **réseau interne** avec le nom du tableau (`wan`, `lan`, `dmz`).
2. Sur **chaque** machine, attribue l'adresse du tableau. Exemple sur FW (adapte les noms d'interface) :

   ```bash
   sudo ip addr add 203.0.113.1/24 dev enp0s3
   sudo ip addr add 192.168.10.1/24 dev enp0s8
   sudo ip addr add 192.168.20.1/24 dev enp0s9
   sudo ip link set enp0s3 up; sudo ip link set enp0s8 up; sudo ip link set enp0s9 up
   ```

   Sur les autres machines : une seule adresse, et la **route par défaut** vers le pare-feu (`sudo ip route add default via 192.168.10.1` sur PC-LAN, par exemple).
3. Sur FW, **active le routage** :

   ```bash
   sudo sysctl -w net.ipv4.ip_forward=1
   echo "net.ipv4.ip_forward=1" | sudo tee /etc/sysctl.d/99-forward.conf
   ```

**J'anticipe.** Sans aucune règle de pare-feu, PC-LAN pourra-t-il joindre SRV-DMZ ? Et EXT pourra-t-il joindre PC-LAN ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Oui aux deux : FW est un **routeur** et, sans règle, il transmet tout. EXT peut joindre PC-LAN **si** EXT connaît une route vers `192.168.10.0/24` (par exemple `sudo ip route add 192.168.0.0/16 via 203.0.113.1`). Ce que le TP va fermer, c'est précisément ce que le routage laisse ouvert par défaut.

</details>

**Point de contrôle :** depuis PC-LAN, `ping 192.168.20.10` répond. Depuis SRV-DMZ, `ping 192.168.10.10` répond aussi (c'est le problème à corriger). Recopie le résultat : ______________________

**Je comprends.** Pourquoi la ligne `net.ipv4.ip_forward=1` est-elle écrite dans un fichier de `/etc/sysctl.d/` en plus de la commande `sysctl -w` ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

`sysctl -w` modifie le réglage du noyau **pour la session en cours** : il disparaît au redémarrage. Le fichier dans `/etc/sysctl.d/` le **rend permanent**.

</details>

## Partie C – La politique par défaut et la matrice (≈ 20 min)

**But :** écrire sur papier ce que le pare-feu devra faire, **avant** de taper une règle.

Complète la matrice des flux de SimIO d'après le cahier des charges :

- les postes internes accèdent au web (80, 443) et au DNS (53) d'Internet ;
- les postes internes administrent le serveur de la DMZ en SSH (22) et consultent son site (80) ;
- Internet accède au site web **uniquement**, sur le port **8080** du pare-feu (redirigé vers le port 80 du serveur) ;
- la DMZ n'a **aucun accès** au LAN ;
- l'administration SSH du pare-feu n'est possible que **depuis le LAN**.

| Source ↓ / Destination → | FW | LAN | DMZ | WAN |
|---|---|---|---|---|
| **LAN** | | | | |
| **DMZ** | | | | |
| **WAN** | | | | |

**J'anticipe.** Quelle sera la politique par défaut des chaînes `input` et `forward` ? Quelle est la conséquence si on oublie d'autoriser les réponses (`established`) ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Politique `drop` partout. Sans la règle `ct state established,related accept`, le pare-feu laisserait passer la **demande** (par exemple vers le web) mais jetterait la **réponse** : rien ne fonctionnerait, même pour les flux autorisés.

</details>

## Partie D – Écrire le jeu de règles nftables (≈ 45 min)

**But :** appliquer la matrice avec `nftables`.

1. Sur FW, `nftables` est installé (préparation) : vérifie `nft --version`.
2. Écris `/etc/nftables.conf` (avec `sudo nano`) :

   ```text
   #!/usr/sbin/nft -f
   flush ruleset

   table inet filtre {
     chain input {
       type filter hook input priority 0; policy drop;
       ct state established,related accept
       ct state invalid drop
       iif "lo" accept
       icmp type echo-request accept
       iifname "enp0s8" tcp dport 22 accept
     }

     chain forward {
       type filter hook forward priority 0; policy drop;
       ct state established,related accept
       ct state invalid drop
       # LAN vers Internet : web et DNS
       iifname "enp0s8" oifname "enp0s3" tcp dport { 80, 443 } accept
       iifname "enp0s8" oifname "enp0s3" udp dport 53 accept
       # LAN vers DMZ : web et administration
       iifname "enp0s8" oifname "enp0s9" tcp dport { 22, 80 } accept
       # Internet vers DMZ : uniquement le web redirigé
       iifname "enp0s3" oifname "enp0s9" ip daddr 192.168.20.10 tcp dport 80 ct status dnat accept
       # DMZ vers LAN : rien (politique par défaut)
     }
   }

   table ip nat {
     chain prerouting {
       type nat hook prerouting priority -100;
       iifname "enp0s3" tcp dport 8080 dnat to 192.168.20.10:80
     }
     chain postrouting {
       type nat hook postrouting priority 100;
       oifname "enp0s3" masquerade
     }
   }
   ```

3. **Vérifie la syntaxe avant d'appliquer** : `sudo nft -c -f /etc/nftables.conf` (aucune sortie = pas d'erreur).
4. Applique : `sudo nft -f /etc/nftables.conf`, puis rends-le permanent : `sudo systemctl enable --now nftables`.
5. Relis ce qui est chargé : `sudo nft list ruleset`.

> [!WARNING]
> **Ne te coupe pas l'accès.** Si tu administres FW par SSH depuis le LAN, la règle `input` du port 22 doit être présente **avant** d'appliquer la politique `drop`. Garde une console VirtualBox ouverte sur FW.

**Je comprends.** Explique, avec tes mots, chacune de ces lignes :

| Ligne | Ce qu'elle fait |
|---|---|
| `ct status dnat accept` | ______________________ |
| `policy drop` dans `forward` | ______________________ |
| `masquerade` dans `postrouting` | ______________________ |
| `dnat to 192.168.20.10:80` | ______________________ |

<details markdown="1">
<summary>Éléments de réponse</summary>

- `ct status dnat accept` : n'accepte que les paquets **qui ont été redirigés** par la règle de NAT destination. Un paquet qui viendrait d'Internet vers le port 80 sans passer par la redirection serait refusé.
- `policy drop` dans `forward` : tout ce qui traverse le pare-feu et n'est pas explicitement autorisé est jeté.
- `masquerade` : remplace l'adresse source des paquets sortant par la WAN par l'adresse du pare-feu ; les réponses reviennent au pare-feu qui les renvoie à la bonne machine.
- `dnat to 192.168.20.10:80` : réécrit la destination (adresse et port) : l'extérieur parle au port 8080 du pare-feu, le serveur reçoit sur son port 80.

</details>

## Partie F – Un accès SFTP restreint pour un prestataire (≈ 30 min)

**But :** un prestataire dépose des fichiers sur SRV-DMZ, **sans accès à la machine** et sans pouvoir sortir de son dossier.

1. Sur SRV-DMZ : crée le groupe et l'utilisateur.

   ```bash
   sudo groupadd sftpusers
   sudo useradd -g sftpusers -d /depot -s /usr/sbin/nologin presta
   echo "presta:MotDePasseTP" | sudo chpasswd     # identifiant de laboratoire
   ```

2. Prépare le dossier : le dossier **racine** de la cage doit appartenir à `root` et ne pas être modifiable par d'autres, le dossier de dépôt à l'utilisateur.

   ```bash
   sudo mkdir -p /srv/sftp/presta/depot
   sudo chown root:root /srv/sftp /srv/sftp/presta
   sudo chmod 755 /srv/sftp /srv/sftp/presta
   sudo chown presta:sftpusers /srv/sftp/presta/depot
   ```

3. À la **fin** de `/etc/ssh/sshd_config`, ajoute :

   ```text
   Match Group sftpusers
       ChrootDirectory /srv/sftp/%u
       ForceCommand internal-sftp
       AllowTcpForwarding no
       X11Forwarding no
   ```

4. Vérifie et recharge : `sudo sshd -t && sudo systemctl reload ssh`.
5. Depuis PC-LAN : `sftp presta@192.168.20.10`, puis `pwd`, `ls`, `put fichier.txt depot/`, `cd ..`.
6. Essaie `ssh presta@192.168.20.10` : que se passe-t-il ?

**J'anticipe.** Pourquoi le dossier `/srv/sftp/presta` doit-il appartenir à `root` ? Que fait `ForceCommand internal-sftp` ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

`sshd` **refuse** une cage dont la racine est modifiable par l'utilisateur (il pourrait la détourner pour s'échapper). `ForceCommand internal-sftp` impose le **sous-système SFTP** : même avec un mot de passe valide, le prestataire n'obtient jamais de terminal.

</details>

**Point de contrôle :** le dépôt fonctionne, `cd ..` reste dans la cage, `ssh` est refusé. Recopie les messages : ______________________
